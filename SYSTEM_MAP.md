# System map

## HTTP endpoints

Access (checked by `AdminAuthorizationIntegrationTests`, which fails if an endpoint declares no policy and no `[AllowAnonymous]`):

- **Admin** (`Admin` policy): every `/api/apps` route except `GET /api/apps/me`, plus `/api/apps/{appKey}/permissions`, `/roles`, `/users`, `/api/users` (sessions included) and `/api/notifications/templates`. They require `Authorization: Bearer <access token>` issued by `POST /api/auth/login` for the reserved `core` application (audience `core`, `typ: at+jwt`) and carrying the `core.admin` permission. Without a token, or with an invalid, expired, foreign or wrongly typed one, they return `401 Auth.InvalidToken` (`WWW-Authenticate: Bearer`). With a valid token without `core.admin` they return `403 Auth.AdminRequired`. M2M credentials are not accepted there.
- **M2M** (`Application` policy, `X-App-Key` + `X-App-Secret`): `GET /api/apps/me`, `/api/notifications` (send, list, get) and `/api/auth/*`.
- **Anonymous**: `/health` and `/.well-known/*`.
- An admin access token stays valid until it expires (at most `Jwt:AccessTokenMinutes`), even if the user is locked or loses `core.admin` meanwhile.

## Request pipeline (`Program.cs`)

1. `UseForwardedHeaders`: takes the client IP and scheme from `X-Forwarded-For` / `X-Forwarded-Proto` (`ForwardLimit = 1`: only the rightmost entry, the one added by the Railway proxy, so clients cannot spoof it). Any proxy is trusted, so the container must only be reachable through Railway's proxy.
2. `CorrelationIdMiddleware`: reads or creates `X-Correlation-Id`, returns it in the response and adds `CorrelationId` to every log line.
3. `UseSerilogRequestLogging`: one log line per request, written to the host's Serilog logger from DI (`options.Logger`), not to the static `Log.Logger`. `AddSerilog` uses `preserveStaticLogger: true`, so each host owns and disposes its logger. The static logger stays the bootstrap console logger of `Program.cs`, used only for startup and fatal errors.
4. `UseExceptionHandler` + `GlobalExceptionHandler`: unhandled exceptions become RFC 7807 `ProblemDetails` (500). Every `ProblemDetails` includes `instance` and `correlationId`.
5. `UseStatusCodePages`: empty error responses (such as 404 or 405) are formatted as `ProblemDetails`.
6. `UseAuthentication` + `UseAuthorization`: no default scheme. The `Application` policy uses the `AppKey` scheme (`AppKeyAuthenticationHandler`, headers `X-App-Key` and `X-App-Secret`, claims `app_id` and `app_key`). The `Admin` policy uses the `Bearer` scheme (`AdminAuthentication`, JwtBearer over the Core's own tokens, `MapInboundClaims = false`, the `app_key` claim added from `client_id`) and requires the claim `permissions` = `core.admin`.
7. `AppKeyLogContextMiddleware`: for authenticated applications, adds `AppKey` to the Serilog `LogContext` (logs written later in the request) and to the request completion log line.
8. `MapControllers`.

- NHibernate `ISessionFactory` (singleton) and `ISession` (scoped per request), registered in `Common/Persistence/NHibernateExtensions.cs`.
- Dialect `PostgreSQL83Dialect`, driver `NpgsqlDriver`.
- Health: `DatabaseHealthService` (scoped, `Common/Persistence/`) runs `SELECT 1` for `GET /health`.
- Mappings: every public `ClassMapping<T>` in the API assembly is picked up automatically (`NHibernateExtensions.BuildSessionFactory` also accepts additional assemblies for tests).
- Mapping conventions: tables and columns in `snake_case` (plural table names), explicit `Table(...)`/`Column(...)`, enums stored as strings (`varchar`), `Id` with `Generators.Assigned`, and audit columns with `NHibernateUtil.UtcDateTime` (`timestamptz`).
- Transactions: reads require no explicit transaction; writes open an explicit transaction (`session.BeginTransaction()` + `CommitAsync`).
- Schema migrations: DbUp (`dbup-postgresql`, `Common/Persistence/DatabaseMigrator.cs`) applies forward-only embedded SQL scripts from `src/Href.Core.Api/Database/Migrations/NNNN_description.sql` on startup (`WithTransactionPerScript`), recording executed scripts in the `schemaversions` journal table. In `Development`, `EnsureDatabase.For.PostgresqlDatabase` creates the database if it does not exist.
- Tables:
  - `applications` (`0001_create_applications.sql`, mapped by `ApplicationMapping`): `id`, `app_key` (unique index `ux_applications_app_key`), `name`, `description`, `status` (`CHECK IN ('Active', 'Suspended')`), `client_secret_hash`, `client_secret_rotated_at_utc`, `allow_self_registration`, `created_at_utc`, `updated_at_utc`.
  - `email_templates` (`0003_create_notifications_and_email_templates.sql`, mapped by `EmailTemplateMapping`): `id`, `key` (unique index `ux_email_templates_key`), `name`, `description`, `subject`, `html_body` (`TEXT`), `text_body` (`TEXT`), `is_system`, `created_at_utc`, `updated_at_utc`.
  - `notifications` (`0003_create_notifications_and_email_templates.sql`, mapped by `NotificationMapping`): `id`, `app_key` (plain column, no FK), `to_email`, `to_name`, `subject`, `html_body` (`TEXT`), `text_body` (`TEXT`), `template_key`, `status` (`CHECK IN ('Pending', 'Processing', 'Sent', 'Failed')`), `attempts`, `max_attempts`, `version` (optimistic concurrency), `next_attempt_at_utc`, `processing_started_at_utc`, `sent_at_utc`, `last_error`, `notify_on_failure_to`, `correlation_id`, `created_at_utc`, `updated_at_utc`; indexes `ix_notifications_status_next_attempt_at_utc` (`status, next_attempt_at_utc`) and `ix_notifications_app_key_created_at_utc` (`app_key, created_at_utc DESC`).

    - `user_application_accesses`: `id`, `user_id` (FK `users`), `application_id` (FK `applications`), `created_at_utc`, `updated_at_utc`; unique index `ux_user_application_accesses_user_id_application_id`, index `ix_user_application_accesses_application_id`.
    - `user_application_access_roles`: `user_application_access_id`, `role_id` (PK of both; FKs `ON DELETE CASCADE`, so deleting a role removes it from every access and revoking an access removes its links); index `ix_user_application_access_roles_role_id`.

Expired rows are not cleaned up yet; a cleanup must delete whole families, since deleting only a successor would leave its `Rotated` predecessor without a replacement.
  - `user_tokens` (`0009_create_user_tokens.sql`, mapped by `UserTokenMapping`; identity columns are `Update(false)`): `id`, `user_id` (FK `users`), `application_id` (FK `applications`), `purpose` (`CHECK` `EmailVerification` \| `PasswordReset`), `token_hash` (exactly 64 characters, unique index `ux_user_tokens_token_hash`), `created_at_utc`, `expires_at_utc` (`> created_at_utc`), `consumed_at_utc`, `revoked_at_utc` (`ck_user_tokens_single_end`: never both).   - Seed `0008_seed_core_admin.sql`: the reserved `core` application (status `Active`, the secret is the hash of a random value nobody knows until `Bootstrap__CoreClientSecret` or a rotation), the permission `core.admin` and the role `admin` with that permission, all with fixed ids (`CoreApplication`). The script aborts if an application with `app_key = 'core'` already exists with another id.
  - `audit_logs` (`0002_create_audit_logs.sql`, mapped by `AuditLogMapping` with `Mutable(false)` and `JsonbType`): append-only table protected by trigger `audit_logs_block_mutation` (`BEFORE UPDATE OR DELETE`), with indexes on `occurred_at_utc DESC`, `(app_key, occurred_at_utc DESC)`, `correlation_id`, and `(entity_type, entity_id)`.
  - Seed `0004_seed_default_email_templates.sql`: inserts the four default system templates into `email_templates` (see `## Email templates`).

## Email templates

Default templates (`is_system = true`, Spanish, simple responsive HTML with inline CSS and no external images, plus `TextBody`) loaded by migration `0004_seed_default_email_templates.sql` with `INSERT ... ON CONFLICT (key) DO NOTHING`. The HTML and text bodies of each template each use exactly the variables listed; the subject uses a subset of them.

| Key | Purpose | Variables |
|-----|---------|-----------|
| `welcome-user` | Welcome email after an account is created. | `UserName`, `AppName` |
| `verify-email` | Link to verify the email address of an account. | `UserName`, `AppName`, `VerificationUrl`, `ExpiresInHours` |
| `reset-password` | Link to reset the password of an account. | `UserName`, `AppName`, `ResetUrl`, `ExpiresInMinutes` |
| `delivery-failed-alert` | Internal operational alert to the application owner when a notification exhausts its retries. | `OriginalTo`, `OriginalSubject`, `NotificationId`, `Attempts`, `LastError` |

- `VerificationUrl` and `ResetUrl` are placed as the full quoted `href` value (and shown as text); the caller must validate them before rendering.
- A migration runs once, so edits made later (for example through the template administration) are never overwritten. Changing a default template means a new migration with an `UPDATE`; the seed never overwrites edits.
- Multi-language templates are out of scope.
- Required and allowed placeholders (`SystemTemplateRequirements`, equal to the table above; a test checks that its keys are the seeded system keys and that each seeded template uses exactly them): an update of a system template (`PUT /api/notifications/templates/{key}`) must contain every listed placeholder, counted across subject + HTML body + text body together (a placeholder missing from the HTML but present in the text is accepted), or it fails with `400 Templates.MissingRequiredPlaceholders` listing the missing ones. It cannot use any other placeholder, because the Core flows never provide it and every send would fail with `Templates.MissingVariables`: `400 Templates.UnknownPlaceholders` lists them. Comparison is case-insensitive. Custom templates have no placeholder rules.
- A system template with no `SystemTemplateRequirements` entry fails closed: its update must keep exactly its current placeholder set. The map keys must equal the `is_system` rows of the database (the consistency test ignores the `tpl-` rows that persistence tests leave behind).
- System templates cannot be deleted (`409 Templates.SystemTemplate`) and their `key` and `isSystem` never change. Clients cannot create system templates.
- `TEMPLATE_DELETED` is recorded in `AuditActions` next to `TEMPLATE_CREATED` and `TEMPLATE_UPDATED`.

## Background processing

The API only queues notifications (outbox pattern); `NotificationBackgroundWorker` delivers them asynchronously through `NotificationDispatcher`.

- **One clock.** Every timestamp (claim, recovery, domain transitions, `Notification.Queue` and `updated_at_utc` from `AuditTimestampListener`) comes from the DI `TimeProvider` and reaches SQL as a `timestamptz` parameter. PostgreSQL `now()` is never used.
- **Recovery** (each iteration, one transaction): raw SQL that mirrors `RecoverStuck` on rows with `status = 'Processing'` and `processing_started_at_utc < @now - StuckAfterMinutes` (`@stuckBefore` computed in C#). `attempts` is untouched; with `attempts >= max_attempts` the row becomes `Failed` with `last_error = 'Processing timed out'` (`Notification.ProcessingTimedOutError`), otherwise `Pending` with `next_attempt_at_utc = @now`; always `processing_started_at_utc = NULL`, `updated_at_utc = @now`, `version = version + 1`. A row recovered as `Failed` with `NotifyOnFailureTo` gets the failure alert in the same transaction.
- **Claim** (one transaction, committed before any send): `WITH claimed AS (SELECT id FROM notifications WHERE status = 'Pending' AND next_attempt_at_utc <= @now AND attempts < max_attempts ORDER BY next_attempt_at_utc, id LIMIT @batch FOR UPDATE SKIP LOCKED) UPDATE notifications ... SET status = 'Processing', attempts = attempts + 1, processing_started_at_utc = @now, updated_at_utc = @now, version = version + 1 ... RETURNING id, version`. `SKIP LOCKED` keeps concurrent claims (several instances) disjoint. A `Pending` row with no attempts left is never claimed.
- **Send and record** (per claimed notification, one after another, each with its own `ISession`): load it and send it only if it is still `Processing` with the `version` returned by the claim; otherwise (another instance recovered it, or recovered and claimed it again) it is skipped with a Warning, which prevents a double send. Then send it with `IEmailSender` and the stopping token, and record `MarkSent` or `RegisterFailure(exception.Message)` in one transaction (back to `Pending` with a 1 or 5 minute backoff, or `Failed` after the 3rd attempt). The record commit never uses the stopping token: a shutdown right after a successful send still records `Sent`. An error in one notification is logged and never stops the rest of the batch; when the send succeeded but the record failed (not a concurrency conflict) it is logged as Error and counted in `DispatchResult.UnexpectedErrors`.
- **Failure alert**: when a notification ends `Failed` (send failure or recovery) and has `NotifyOnFailureTo`, a new notification is queued in the same transaction from the `delivery-failed-alert` template (`OriginalTo`, `OriginalSubject`, `NotificationId`, `Attempts`, `LastError`) with the original `AppKey` and `CorrelationId`, `ToEmail = NotifyOnFailureTo` and `NotifyOnFailureTo = null`, so an alert never triggers another alert. The alert exists only if the `Failed` state was committed. A missing template or a rendering or validation error is logged as Error and the `Failed` state is still committed.
- **Shutdown**: a claimed notification that is not sent yet when the host stops, or whose send is cancelled by the stopping token, is released with `ReleaseUnsent`: back to `Pending` at once and the attempt is given back (`attempts - 1`), so a shutdown never makes a notification `Failed` nor triggers an alert. A cancelled send may already have been accepted by the SMTP server; it is sent again later (at-least-once). If the process is killed before it records anything (for example a Railway redeploy that outlasts the host shutdown timeout), the row stays `Processing` until the recovery releases it after `StuckAfterMinutes` (that attempt stays counted).
- **Optimistic concurrency**: when the recovery changed a row while it was being sent, the record commit fails with `StaleStateException`; it is logged as a Warning, nothing is recorded for that row and the batch continues.
- **At-least-once delivery**: an email can be sent twice when the send succeeds but its result is not recorded (commit failure, crash or redeploy after the send, a recovery of a row whose send took longer than `StuckAfterMinutes`, or a cancelled send that the server had already accepted). Keep `StuckAfterMinutes` well above `BatchSize` × the worst-case send time (each SMTP operation is bounded by `Smtp:TimeoutSeconds`); `NotificationWorkerStartupCheck` warns at startup when `StuckAfterMinutes * 60 < BatchSize * Smtp:TimeoutSeconds`.
- **Logs**: every log written while one notification is processed (dispatcher and `IEmailSender`) carries `NotificationId`, `AppKey` and `CorrelationId` in the Serilog `LogContext`, pushed in the same method that processes the notification. The dispatcher messages also include `{NotificationId}` in the text, because the console template only shows `CorrelationId` and `AppKey`. Bodies are never logged. The dispatcher never logs subjects or recipient addresses, but `SmtpEmailSender` logs the recipient at Debug (`Email sent to {ToEmail}`) and SMTP error messages, logged as is with the failure, may contain addresses.

The API does not start without a valid `Smtp` section (`ValidateOnStart`): `Host` and `FromEmail` required, `Port` in 1..65535, defined `SecureSocket`, valid `FromEmail`, `Username` and `Password` both set or both empty, and no credentials with `SecureSocket = None`. `appsettings.json` carries the Gmail defaults without secrets; `appsettings.Development.json` points to Mailpit (`localhost:1025`, `None`, no credentials); the `api` service in `docker-compose.yml` talks to the `mailpit` service.

The API does not start without a valid `Jwt` section (`ValidateOnStart`, see `JwtOptionsValidator`). Outside Development a signing key is required: the `api` service in `docker-compose.yml` runs as `Production` and takes the key from the host variable `JWT_SIGNING_PRIVATE_KEY_PEM` (and optionally `JWT_SIGNING_KEY_ID`, default `local-1`), with `Jwt__Issuer=http://localhost:8080`; `.env.example` lists the same `Jwt__*` variables with an empty key. Key generation and rotation: `docs/instructions.md`.
