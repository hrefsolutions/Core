## Request pipeline (`Program.cs`)

1. `UseForwardedHeaders`: takes the client IP and scheme from `X-Forwarded-For` / `X-Forwarded-Proto` (`ForwardLimit = 1`: only the rightmost entry, the one added by the Railway proxy, so clients cannot spoof it). Any proxy is trusted, so the container must only be reachable through Railway's proxy.
2. `CorrelationIdMiddleware`: reads or creates `X-Correlation-Id`, returns it in the response and adds `CorrelationId` to every log line.
3. `UseSerilogRequestLogging`: one log line per request.
4. `UseExceptionHandler` + `GlobalExceptionHandler`: unhandled exceptions become RFC 7807 `ProblemDetails` (500). Every `ProblemDetails` includes `instance` and `correlationId`.
5. `UseStatusCodePages`: empty error responses (such as 404 or 405) are formatted as `ProblemDetails`.
6. `UseAuthentication` + `UseAuthorization`: scheme `AppKey` (`AppKeyAuthenticationHandler`, headers `X-App-Key` and `X-App-Secret`, claims `app_id` and `app_key`) and policy `Application`.
7. `AppKeyLogContextMiddleware`: for authenticated applications, adds `AppKey` to the Serilog `LogContext` (logs written later in the request) and to the request completion log line.
8. `MapControllers`.

- Dialect `PostgreSQL83Dialect`, driver `NpgsqlDriver`.
- Health: `DatabaseHealthService` (scoped, `Common/Persistence/`) runs `SELECT 1` for `GET /health`.

In `Development`, `EnsureDatabase.For.PostgresqlDatabase` creates the database if it does not exist.

## Background processing

The API only queues notifications (outbox pattern); `NotificationBackgroundWorker` delivers them asynchronously through `NotificationDispatcher`.

- **One clock.** Every timestamp (claim, recovery, domain transitions, `Notification.Queue` and `updated_at_utc` from `AuditTimestampListener`) comes from the DI `TimeProvider` and reaches SQL as a `timestamptz` parameter. PostgreSQL `now()` is never used.
- **Recovery** (each iteration, one transaction): raw SQL that mirrors `RecoverStuck` on rows with `status = 'Processing'` and `processing_started_at_utc < @now - StuckAfterMinutes` (`@stuckBefore` computed in C#). `attempts` is untouched; with `attempts >= max_attempts` the row becomes `Failed` with `last_error = 'Processing timed out'` (`Notification.ProcessingTimedOutError`), otherwise `Pending` with `next_attempt_at_utc = @now`; always `processing_started_at_utc = NULL`, `updated_at_utc = @now`, `version = version + 1`. A row recovered as `Failed` with `NotifyOnFailureTo` gets the failure alert in the same transaction.
- **Claim** (one transaction, committed before any send): `WITH claimed AS (SELECT id FROM notifications WHERE status = 'Pending' AND next_attempt_at_utc <= @now AND attempts < max_attempts ORDER BY next_attempt_at_utc, id LIMIT @batch FOR UPDATE SKIP LOCKED) UPDATE notifications ... SET status = 'Processing', attempts = attempts + 1, processing_started_at_utc = @now, updated_at_utc = @now, version = version + 1 ... RETURNING id, version`. `SKIP LOCKED` keeps concurrent claims (several instances) disjoint. A `Pending` row with no attempts left is never claimed.
- **Send and record** (per claimed notification, one after another, each with its own `ISession`): load it and send it only if it is still `Processing` with the `version` returned by the claim; otherwise (another instance recovered it, or recovered and claimed it again) it is skipped with a Warning, which prevents a double send. Then send it with `IEmailSender` and the stopping token, and record `MarkSent` or `RegisterFailure(exception.Message)` in one transaction (back to `Pending` with a 1 or 5 minute backoff, or `Failed` after the 3rd attempt). The record commit never uses the stopping token: a shutdown right after a successful send still records `Sent`. An error in one notification is logged and never stops the rest of the batch; when the send succeeded but the record failed (not a concurrency conflict) it is logged as Error and counted in `DispatchResult.UnexpectedErrors`.
- **Failure alert**: when a notification ends `Failed` (send failure or recovery) and has `NotifyOnFailureTo`, a new notification is queued in the same transaction from the `delivery-failed-alert` template (`OriginalTo`, `OriginalSubject`, `NotificationId`, `Attempts`, `LastError`) with the original `AppKey` and `CorrelationId`, `ToEmail = NotifyOnFailureTo` and `NotifyOnFailureTo = null`, so an alert never triggers another alert. The alert exists only if the `Failed` state was committed. A missing template or a rendering or validation error is logged as Error and the `Failed` state is still committed.
- **Shutdown**: a claimed notification that is not sent yet when the host stops, or whose send is cancelled by the stopping token, is released with `ReleaseUnsent`: back to `Pending` at once and the attempt is given back (`attempts - 1`), so a shutdown never makes a notification `Failed` nor triggers an alert. A cancelled send may already have been accepted by the SMTP server; it is sent again later (at-least-once). If the process is killed before it records anything (for example a Railway redeploy that outlasts the host shutdown timeout), the row stays `Processing` until the recovery releases it after `StuckAfterMinutes` (that attempt stays counted).
- **Optimistic concurrency**: when the recovery changed a row while it was being sent, the record commit fails with `StaleStateException`; it is logged as a Warning, nothing is recorded for that row and the batch continues.
- **At-least-once delivery**: an email can be sent twice when the send succeeds but its result is not recorded (commit failure, crash or redeploy after the send, a recovery of a row whose send took longer than `StuckAfterMinutes`, or a cancelled send that the server had already accepted). Keep `StuckAfterMinutes` well above `BatchSize` × the worst-case send time (each SMTP operation is bounded by `Smtp:TimeoutSeconds`); `NotificationWorkerStartupCheck` warns at startup when `StuckAfterMinutes * 60 < BatchSize * Smtp:TimeoutSeconds`.
- **Logs**: every log written while one notification is processed (dispatcher and `IEmailSender`) carries `NotificationId`, `AppKey` and `CorrelationId` in the Serilog `LogContext`, pushed in the same method that processes the notification. The dispatcher messages also include `{NotificationId}` in the text, because the console template only shows `CorrelationId` and `AppKey`. Bodies are never logged. The dispatcher never logs subjects or recipient addresses, but `SmtpEmailSender` logs the recipient at Debug (`Email sent to {ToEmail}`) and SMTP error messages, logged as is with the failure, may contain addresses.
